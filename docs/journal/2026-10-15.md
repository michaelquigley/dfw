# Fullscreen

F11 is opt-in. The brief asked for it in every Linux window, so the first build bound it unconditionally; both terminus rounds held that against honest-opt-in, since an unset option must leave a window unchanged and some product may want F11 for its page. Michael chose the opt-in: `EnableFullscreen` binds F11 as `EnableZoom` binds the zoom chords, and `Fullscreen` binds it too, because a window opened fullscreen needs a way out. Screeningroom's client sets `EnableFullscreen` always, so F11 works there whether or not it opens fullscreen. Without either option no controller is made, and a window the window manager makes fullscreen saves its bounds as before. F11 with any modifier passes through. The fullscreen handler sits on `key-press-event` beside the zoom handler; they never compete because zoom only takes Control chords.

`dfw_fullscreen.fullscreen` is set only from `window-state-event`, never from the request, so `Fullscreen()` is false until the window manager reports the change, including just after an initial `Fullscreen: true`.

While fullscreen, `SaveWindowState` writes `desktopWebView.windowed`, the size and location chosen at startup, instead of the bounds tracker's. A windowed resize earlier in the same session is lost if the window then closes fullscreen. This was deliberate: snapshotting the size on F11 would not cover a window manager's own fullscreen shortcut, and the tracker cannot tell a fullscreen configure event from a windowed one by its timing.

Windows is staged, not supported: `fullscreen_unsupported.go` covers it as a documented no-op, and `docs/future/roadmap/windows-fullscreen.md` names the work to come.

Unverified: no GTK window was driven here, since there is no headless display or window manager on this host. F11, opening fullscreen, the state tracking, and the saved windowed bounds wait for a real-window check, first in screeningroom's client.
