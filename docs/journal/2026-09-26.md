# Go / JavaScriptCore signal coexistence

The tempting `JSC_SIGNAL_FOR_GC` environment fix is not clean on the tested WebKitGTK 2.52.6: its threading code reads the variable, but JSC's separate option parser also rejects it as an invalid option. Use the optional exported `JSConfigureSignalForGC` entry point, resolved dynamically, rather than setting that variable or resetting Go's handler. The native probe showed signal 34 available on this glibc/Go stack; the implementation deliberately derives availability from libc's range and current dispositions/mask rather than encoding 34.

The private setter cannot reveal a prior programmatic choice before initialization and permits overwriting it. The explicit `DFW_DISABLE_JSC_SIGNAL_SETUP` escape hatch is for such embedders, not a cosmetic preference to remove. The process decision and handler checks are startup coordination, not protection against another library racing signal initialization. No production GTK window was driven by the agent; `make test-jsc` exercises the real VM and handlers in fresh processes, while the product close check waits on release adoption.
